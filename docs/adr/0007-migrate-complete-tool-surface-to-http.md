# Migrate the complete tool surface to HTTP

The first HTTP-backed `multica-mcp` implementation should cover the complete existing CLI-backed tool surface rather than only the minimal Hermes delegation path. This includes project tools, autopilot tools and triggers, issue/comment/run/message tools, runtime/agent tools, attachment tools, workspace discovery, and workspace member tools.

**Rationale:** a delegation-only migration would achieve the immediate Hermes remote-agent loop, but it would leave `multica-mcp` in a long-lived mixed mode where some tools use direct HTTP and others still depend on CLI installation/profile state. Migrating the whole current tool surface makes the adapter easier to reason about, deploy, test, and document.

**Consequences:** implementation scope is larger because project and autopilot endpoints must be mapped and tested as well as the delegation-critical endpoints. If an existing CLI-backed tool has no HTTP endpoint, the migration should identify the missing backend API explicitly rather than silently retaining CLI fallback in production HTTP mode. CLI-backed mode may remain an explicit development/debug backend, but production HTTP mode must not partially shell out to the CLI.

**HTTP client boundary:** direct HTTP calls should live behind a shared client module such as `src/lib/multica-http-client.ts`. Tool implementations should call typed domain helpers such as `listWorkspaces`, `createIssue`, or `listAgents` rather than embedding ad-hoc `fetch()` calls or knowing endpoint path/body details. The shared client may have a private/generic request layer underneath, but the public surface used by tools should be domain-oriented and uniform. The shared client owns base URL resolution, bearer-token headers, timeout behavior, JSON parsing, structured error mapping, endpoint mapping tests, and secret redaction.

**Timeout policy:** use operation-class timeouts rather than a single universal timeout or per-tool timeout parameters everywhere. Read/list/get operations should default to 10_000ms. Write operations such as create/update/comment should default to 20_000ms. Wait/poll operations may expose a `timeout_seconds` tool input with default 300s, maximum 600s, and internal poll interval default 5s. Ordinary read/write tools should not expose timeout arguments because that adds schema noise and encourages inconsistent caller behavior. Environment overrides may tune class defaults, but the operation classification should remain fixed in the client/tool layer.

**Retry policy:** retry only safe idempotent reads and single wait/poll requests. Retry transient network failures, 502/503/504, and 429 only when `Retry-After` is present and within the operation budget. Do not automatically retry writes or side-effecting operations such as create issue, add comment, update issue, cancel, rerun, or anything that could duplicate effects. Use small bounded exponential backoff, for example 250ms, 1s, then 2s, with max attempts 3. Structured errors should include `retryable: true/false` and sanitized attempt count/details, without leaking request bodies, bearer tokens, or raw headers.

**Wait tool boundary:** keep a Multica-local `multica_wait_issue` tool, but limit it to synchronous short waits and immediate state observation. It should not replace the wakeup service. Use `multica_wait_issue` when the caller is already inside a turn and wants to wait briefly for a likely-near-term issue/run completion or collect the latest terminal messages. Use wakeup scheduling for long-running delegation where Hermes should resume in a future turn without holding the MCP/tool call open. Both layers may coexist: Multica owns issue/run polling semantics, while wakeup owns asynchronous Hermes continuation. `multica_wait_issue` should report whether completion came from the issue or the latest run via `completion_scope: "issue" | "latest_run"`.

**Long-running delegation flow:** after creating a Multica issue for a remote agent, prefer a short initial `multica_wait_issue` call before scheduling wakeup. The short wait should catch immediate validation failures, fast completions, or early terminal run messages without unnecessary scheduler noise. If the short wait times out, schedule a wakeup rather than extending the same MCP call to the maximum timeout. The wakeup prompt should include at least `workspace_id`, `issue_id`, the expected agent/runtime when known, the original user goal, and what result should be summarized. This yields the default orchestration: create issue -> short wait, for example 30-60s -> if incomplete, schedule wakeup to poll issue/runs/messages later.

**Wakeup continuation limit:** when a wakeup fires and the Multica issue is still not terminal, Hermes may run one bounded `multica_wait_issue` pass, for example 120-300s, before deciding whether to schedule another wakeup. It must not create an unbounded continuation loop. Wakeup metadata or prompt state should carry a deadline and/or max continuation count, plus the current attempt number. The default balanced continuation schedule is: first wakeup after 300s, follow-up wakeups every 600s, `max_continuation_count: 6`, and `max_elapsed_seconds: 3600`. If the limit is reached while the issue is still running, Hermes should report that the issue is still in progress, include the human-facing URL when available, summarize the latest observed run/messages, and stop automatic tracking unless the user asks to continue.

**Automatic rerun policy:** Hermes may automatically rerun a failed Multica issue at most once, and only when the failure is clearly infrastructure/transient rather than semantic. Eligible reasons include runtime disconnected, worker lost, transient API/network failure, or a task that never actually started. Do not automatically rerun test failures, compile failures, agent-reported semantic failures, permission/auth failures, or user tasks that are intrinsically not achievable. Any automatic rerun must record `rerun_count`, previous run id/status, and the rerun reason in wakeup metadata or prompt state. If `rerun_count >= 1`, report the failure and stop automatic rerun unless the user explicitly asks to retry.

**Failure evidence and full-artifact access:** default failure summaries should be bounded but useful: include the latest run id/status/url when available and up to the last 100 run messages, truncating long per-message text/output fields to roughly 2k-4k characters. Do not return complete logs or complete artifacts in the default wait/wakeup result because they can pollute Hermes context and leak excessive environment detail. Instead, expose explicit retrieval paths so an agent can investigate on demand: paginated/incremental run-message queries such as `multica_issue_run_messages` with `since`, and attachment/file download tools such as `multica_attachment_download`. Full artifacts should be pulled only when needed for diagnosis or user-requested inspection.

**Agent selection policy:** Hermes should select an assignee agent, not a raw runtime, when creating a Multica issue. If the user gives an exact `assignee_id` or exact assignee name, Hermes may use it directly. Otherwise Hermes should list/filter available agents for the target machine/runtime/provider implied by the user and task, prefer non-archived agents on online or recently-seen runtimes, then ask the user to confirm the proposed assignee before creating the issue. The confirmation should show the agent name/id, machine/runtime/provider, and selection reason. Hermes must not silently assign a random first available agent. If no suitable agent exists on the requested machine, report the available alternatives and ask the user rather than guessing. Automatic rerun may switch agents only for the infra/transient cases covered by the rerun policy and should still prefer the same provider/machine family unless the user approves otherwise.

**Task envelope:** Hermes-created Multica issues should use a fixed markdown description envelope rather than arbitrary prose or an over-constrained MCP schema. The envelope should include: `Goal`, `Context`, `Target workspace / repo` (workspace id, repo, working directory, branch), `Constraints` (for example do not commit/push unless requested, ask/report before destructive actions, respect repo conventions), `Expected output` (summary, commands run, verification result, files changed or PR URL when applicable), `Verification` (test/lint/typecheck commands or acceptable fallback), and `Continuation metadata` (originating Hermes session, issue tracking expectations, wakeup policy for long-running work). This keeps remote agents self-sufficient without making every task field a rigid schema requirement.

**Cancel/stop semantics:** in the context of a currently running remote agent, an unqualified user request like "stop it" or "停掉" should default to cancelling the latest/current run/task, not cancelling the whole issue and not merely stopping Hermes tracking. This maps to task/run cancellation, for example `multica_cancel_task` with the latest run UUID. Cancelling the whole issue is a distinct explicit semantic such as "cancel this issue" or "这个任务不要了" and should update the issue status to `cancelled`. Stopping Hermes follow-up/tracking is another distinct semantic such as "stop tracking" or "不用再提醒我" and should only cancel wakeups/continuations without touching the Multica run or issue. If the user wording is ambiguous and more than one destructive action is plausible, ask for confirmation; otherwise use the default run-cancel interpretation for active remote execution.

**Permission and safety boundaries:** classify tool use by risk. Safe/read operations such as listing workspaces, agents, runtimes, issues, runs, and messages may run without extra confirmation once the user's target is clear. Expected writes such as creating an issue, adding a comment, updating ordinary issue metadata, rerunning an issue, or cancelling the current run may proceed when the user's intent is explicit in the conversation. Destructive or sensitive actions require explicit confirmation or unambiguous wording: cancelling the whole issue, deleting/archiving agents/projects/autopilots, changing an agent runtime/custom args/env, crossing to another workspace, using a custom download path, or downloading files that appear large or sensitive. Workspace-scoped tools must require explicit `workspace_id`. Attachment downloads should default to an MCP-managed download directory and return the saved path; custom output paths or sensitive/large artifacts require confirmation. Tool schemas must not accept or echo token-like values; `custom_env` and bearer-token material must be redacted from logs and tool outputs.

**HTTP client result shape:** shared-client domain methods should return a typed result internally, for example `{ ok: true, data } | { ok: false, error }`. They should not throw for expected API/network/auth/validation failures and should not expose raw backend JSON directly to tools. Tool wrappers can then mechanically return `result.data` on success or the structured `result.error` on failure, preserving natural MCP success payloads while keeping failure handling explicit.

**Backend response mapping:** backend HTTP responses should be converted inside the shared client into stable domain DTOs. Tool implementations should not depend on raw backend JSON shapes; they should only perform MCP presentation of the DTO, such as adding or omitting optional human-facing URLs. Backend API shape changes should be isolated to client endpoint/DTO mapping tests rather than requiring every tool wrapper to change.

**DTO type location:** shared domain DTO types should live in `src/lib/multica-types.ts`, not inside `src/lib/multica-http-client.ts` and not repeated per tool. The HTTP client and tool wrappers can both import these stable types, while the client remains focused on transport/mapping behavior and can later be split without moving the DTO contract.

**DTO naming:** keep two type families when HTTP response shape differs from the MCP/domain shape. Use `Api*Response` names, such as `ApiIssueResponse`, for raw backend response types consumed by the shared client. Use `Multica*` names, such as `MulticaIssue`, `MulticaWorkspace`, or `MulticaRunMessage`, for stable domain DTOs returned by client domain methods and presented by tool wrappers. Client mapping tests should explicitly cover `Api*Response` to `Multica*` conversion.

**Runtime validation:** treat backend HTTP responses as an external input boundary. Define Zod schemas for key backend response shapes, infer `Api*Response` types from those schemas, then map to stable `Multica*` DTOs. The first pass should prioritize delegation-critical endpoints such as create/list issue, workspace discovery, wait/status, runs, and run messages. Validation can be pragmatic rather than maximally strict: required fields should be checked, while non-critical unknown fields may be ignored or accepted with `.passthrough()`. Caller/tool input validation failures should use `validation_failed`. Backend response schema drift should be treated as an adapter/backend contract problem and returned as `internal_error` with sanitized details such as `source: "backend_response_validation"`, endpoint/operation, and safe issue summaries; raw Zod output should not leak to tool callers.

**Rollout checkpoint:** startup validation should fail fast on configuration mistakes such as missing/invalid `MULTICA_BACKEND`, missing/malformed `MULTICA_API_BASE_URL`, or missing `MULTICA_TOKEN`, but should not ping or block on backend readiness at startup. The first-phase deployment checkpoint should be an end-to-end API-backed validation, not read-only only: verify the MCP server starts, environment is parsed, workspace discovery works, explicit `workspace_id` list-agents/list-runtimes calls work, then create a clearly marked Test Issue and confirm via API readback that issue creation, stable identifiers, assignee linkage when used, run/status/message retrieval, and human-facing URL construction work. The Test Issue should be titled/labelled as a checkpoint artifact and should not be hidden. Most validation should be performed automatically by the agent; the user may inspect for incorrect content, but routine API consistency checks should not require manual review. Destructive cleanup, if any, follows the normal explicit issue-cancel semantics.

**Fallback policy:** when `MULTICA_BACKEND=http` is selected, per-tool CLI fallback is forbidden. Warnings are not enough because fallback would hide incomplete migration and reintroduce PATH/profile/auth drift into production.

**Missing coverage errors:** use `missing_backend_endpoint` when the Multica backend does not expose the HTTP API needed for an existing CLI-backed operation. Use `not_implemented` when the backend API exists or is expected to exist, but `multica-mcp` has not wired that HTTP adapter path yet. Both errors should be structured tool errors with sanitized details identifying the tool and operation.
