# Use internal Multica backend alias for Hermes deployment

For the self-hosted Hermes deployment, `multica-mcp` should call the Multica backend through the private Docker network at `http://multica-backend:8080`, not through the public `https://kanban-api.lumeny.io` endpoint. The MCP server must keep the API origin configurable via a Multica API Base URL so local development and non-co-located deployments can still use a public endpoint, but the production Hermes wiring should require the `multica-backend` network alias to be reachable from the `multica-mcp` runtime.

**Consequences:** the Hermes/agent container must join a Docker network where `multica-backend` resolves to the Multica backend service; the Multica compose/service wiring should provide that alias rather than exposing the generic service name `backend` as the integration contract. Reachability is a deployment responsibility. `multica-mcp` should not auto-fallback to the public API domain when the internal alias fails.

**Startup policy:** `MULTICA_BACKEND` has no default value; deployments must explicitly set it to `http` or `cli`. If it is unset or set to an unknown value, the MCP server should fail fast at startup rather than silently selecting a backend. During the HTTP migration stage, `MULTICA_BACKEND=http` should also fail fast at server startup if required HTTP configuration is missing or obviously invalid, including a missing `MULTICA_API_BASE_URL`, malformed API URL, or missing `MULTICA_TOKEN`. Startup should not actively ping `MULTICA_API_BASE_URL`; backend reachability and readiness are runtime/deployment concerns. Runtime network/API failures after startup should still be returned as structured tool errors such as `api_unreachable` or `auth_failed`, and deployments that need readiness gating should use an external healthcheck rather than blocking MCP server startup.
